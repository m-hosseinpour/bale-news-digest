# Bale News Digest

دریافت خودکار اخبار از کانال بله، سنجش اهمیت و خلاصه‌سازی با هوش مصنوعی، و ارسال خلاصه به کانال بله.

## امکانات

- جمع‌آوری پیام‌های جدید کانال از API عمومی وب بله (بدون مرورگر)
- سنجش اهمیت هر خبر با یک فراخوانی LLM (`major`/`normal`/`trivial`)
- خلاصه‌سازی اخبار مهم و ارسال به کانال با بات بله
- ارسال عکس/ویدیو/صوت/فایل همراه خلاصه، بدون دانلود یا آپلود سمت ما
- ذخیره پیام‌های دیده‌شده در `news_posts.json`
- Webhook برای پاسخ ثابت به پیام‌های خصوصی ربات

## پیش‌نیازها

- Python 3.11+
- uv

نیازی به مرورگر، Chromium یا Playwright نیست: جمع‌آوری از طریق
`POST https://api.ble.ir/api/v1/LoadHistory` انجام می‌شود.

## نصب پروژه

```shell
uv sync
cp .env.example .env
```

## تنظیمات `.env`

حداقل مقادیر لازم:

```env
BALE_BOT_TOKEN=
BALE_BOT_CHAT_ID=
OPEN_AI_API_KEY=
CHANNEL_SLUG=akharinkhabar
PEER_ID=533692756
```

### پیدا کردن `PEER_ID`

آیدی داخلی کانال در API بله **با آیدی Bot API یکی نیست** و باید یک‌بار استخراج شود.
اسکریپت زیر این کار را انجام می‌دهد:

```shell
uv run python scripts/resolve_peer_id.py akharinkhabar
```

خروجی چیزی شبیه این است:

```text
✓ آیدی داخلی کانال akharinkhabar: 533692756
این خط را در .env بگذار:
PEER_ID=533692756
```

همان خط را در `.env` کپی کن. ربات در زمان اجرا دیگر این مقدار را دوباره کشف نمی‌کند؛
اگر `PEER_ID` تنظیم نشده باشد، اجرا با یک خطای واضح فارسی متوقف می‌شود.

`CHANNEL_SLUG` نام عمومی کانال است و هم برای ساخت لینک خبر و هم برای حذف امضای
تبلیغاتی کانال از متن استفاده می‌شود.

### سایر کلیدهای اختیاری

```env
MAX_PAGES_PER_RUN=50      # سقف صفحه در هر اجرا (هر صفحه ۱۰ پیام)
MAX_POSTS_PER_RUN=500     # سقف پست جدید در هر اجرا
MAX_STORED_POSTS=5000     # چند پست در news_posts.json نگه داشته شود
HISTORY_PAGE_SLEEP=0.3    # مکث بین صفحه‌ها (ثانیه)
HTTP_TIMEOUT=30           # timeout درخواست‌ها (ثانیه)
```

### فیلتر اهمیت

هر پست **یک** فراخوانی LLM می‌گیرد و همان تصمیم ارسال را می‌سازد: اگر اهمیتش
به آستانه برسد به کانال می‌رود، وگرنه نه. دستهٔ خبری جداگانه‌ای سنجیده نمی‌شود
(قبلاً یک فراخوانی برای دسته و یک فراخوانی دیگر برای اهمیتِ دسته‌های مهم بود؛
~۴۳٪ فراخوانی کمتر).

```env
MIN_IMPORTANCE=major      # major | normal | trivial
```

پرامپت اهمیت، تبلیغ را همیشه `trivial` می‌گذارد و ورزش/فرهنگی را فقط در
استثناهای عمدی `major` می‌کند: «عنوان بزرگ» (قهرمانی/صعود ملی) برای ورزش، و
«مرگ چهرهٔ ملی» برای فرهنگ و هنر. اگر متنی چکیدهٔ چند خبر باشد (مثل
«آخرین خبرهای کوتاه»)، اهمیت مهم‌ترین خبرِ داخلش ملاک است. «شعار و motto»
فقط وقتی `trivial` است که هیچ واقعهای را گزارش نکند؛ نقل‌قولی که به یک شخص
یا نهاد مشخص نسبت داده شده باشد بیانیه است، هرچند لحنش شعارگونه باشد.

- `major`: فقط رویداد مشخصی که رخ داده و پیامد دارد (حمله، تصمیم رسمی، شوک
  اقتصادی، فاجعه). سخت‌گیرانه‌ترین حالت و کم‌ترین حجم.
- `normal`: رویداد + اظهارنظر/بیانیه/دیدار رسمی.
- `trivial`: عملاً چیزی ارسال نمی‌شود مگر خبرهای بسیار مهم.

اگر سنجش اهمیت شکست بخورد (پاسخ خالی/بی‌ربط مدل)، پست **فرستاده می‌شود**
(fail-open) تا خبر بی‌صدا از دست نرود.

### خلاصه‌سازی چکیده‌ها

پست چکیده («آخرین خبرهای کوتاه») فهرستی از چند خبر جداست، نه یک خبر. خلاصه‌ساز
از این فهرست فقط خبرهایی را می‌آورد که به معیار `major` می‌خورند و هر خبر را در
یک خط جدا می‌نویسد:

- خبرهای کم‌اهمیت چکیده (اظهارنظر، ادعا و تکذیب، پیش‌بینی، دیدار، نتیجهٔ
  مسابقه، هوا، ترافیک، عوارض، دستگیری، اطلاعیهٔ اداری، تغییر جزئی قیمت) در
  خلاصه نمی‌آیند.
- هدر چکیده، بولت‌ها، ایموجی‌ها و خط امضا/تبلیغ خبر نیستند و در خلاصه نمی‌آیند —
  در چکیده قانون ۶ (برگرداندن متن ورودی دست‌نخورده) اعمال نمی‌شود.
- اگر هیچ خبری از این صافی رد نشود، فقط مهم‌ترین خبر چکیده در یک خط می‌آید؛
  خروجی هیچ‌وقت خالی نمی‌شود. تنها استثنا فهرستی است که تمامش تبلیغ و خط
  تبلیغاتی است: در آن حالت فقط نام چیزی که تبلیغ می‌شود می‌آید، بدون قیمت،
  هندل، لینک و فراخوان اقدام.
- اگر متن یک خبر پیوسته باشد (نه فهرست) — حتی اگر روی چند خط شکسته شده باشد —
  همان پاراگراف فشرده نوشته می‌شود و به خط‌ها شکسته نمی‌شود.

معیاری که خلاصه‌ساز در پرامپت خودش آورده همان معیار `major` گیت اهمیت است، ولی
انتخاب را خودش و مستقل از گیت انجام می‌دهد؛ پس در موارد نادر ممکن است با خبری که
باعث ارسال پست شده فرق کند.

اگر از webhook ربات استفاده می‌کنی:

```env
PUBLIC_WEBHOOK_URL=https://your-domain.com/webhook
```

همهٔ پست‌های مهم فقط به کانال اصلی (`BALE_BOT_CHAT_ID`) ارسال می‌شوند؛
کانال اختصاصی برای دسته‌ها وجود ندارد و تنها معیار ارسال، آستانهٔ اهمیت است.

## تست‌ها

تست‌های واحد به شبکه کاری ندارند:

```shell
uv run pytest
```

برای بررسی سلامت جمع‌آوری روی داده واقعی (شمارش نوع پیام‌ها و نرخ تطبیق `sid`
با `news_posts.json`):

```shell
uv run python scripts/verify_collector.py        # ۱۰۰ پیام آخر
uv run python scripts/verify_collector.py 300    # یا هر تعداد دلخواه
```

برای سنجش اثر یک تغییر در پرامپت خلاصه‌ساز، طول خلاصه روی نمونه‌ای از
پست‌های واقعی اندازه‌گیری می‌شود (طول، تعداد جمله، و نرخ حفظ عددهای متن اصلی).
اول نمونه را با پرامپت فعلی فریز کن، بعد از تغییر پرامپت همان نمونه را دوباره
بسنج:

```shell
uv run python scripts/measure_summary_length.py --out measurements/before.json --save-sids measurements/sample.sids.json
# پس از ویرایش پرامپت:
uv run python scripts/measure_summary_length.py --out measurements/after.json --sids measurements/sample.sids.json
```

فریزکردن نمونه لازم است: `news_posts.json` هر ۱۵ دقیقه با اجرای تایمر رشد
می‌کند و بدون فهرست `sid`، نمونهٔ تصادفی بین دو اجرا جابه‌جا می‌شود و مقایسه
بی‌جفت می‌ماند. گیتوی مدل‌ها را round-robin می‌کند، پس نتیجه نویزی است و باید با
میانه مقایسه شود، نه با یک اجرا.

```shell
curl http://127.0.0.1:8001/health
```

بعد از اینکه آدرس عمومی webhook با HTTPS آماده شد:

```shell
uv run python set_webhook.py
```

```text
/webhook
```

## نکات

- خروجی اجرا در لاگ و در `news_posts.json` ذخیره می‌شود.
- اگر مدل پاسخ خالی یا بی‌استفاده برگرداند (بعضی backendهای گیتوی به‌جای
  پاسخ، یک پیام بی‌ربط به زبان دیگر می‌دهند)، تا ۳ بار دوباره تلاش می‌شود —
  هم در سنجش اهمیت (پاسخی که هیچ برچسب معتبری ندارد) و هم در خلاصه‌ساز
  (پاسخی که فارسی نیست).
- در سنجش اهمیت، **خطای انتقالی** (timeout یا قطع اتصال گیتوی) هم مثل پاسخ
  بی‌استفاده تلاش مجدد می‌گیرد؛ فقط اگر هر ۴ تلاش (پشت سر هم، با یک ثانیه
  مکث) شکست بخورد پست با `importance=None` ذخیره و fail-open فرستاده می‌شود.
- اگر خلاصه‌ساز بعد از تلاش‌ها پاسخ قابل استفاده نگیرد، اجرا با خطا متوقف
  می‌شود و آن پست در `news_posts.json` ذخیره نمی‌شود، پس در اجرای بعدی دوباره
  پردازش می‌شود.
- اگر سنجش اهمیت بعد از تلاش‌ها پاسخ قابل استفاده نگیرد، `news_collector` آن
  استثنا را می‌گیرد و `importance=None` ذخیره می‌کند؛ در ارسال fail-open
  رفتار می‌کنیم و پست **فرستاده می‌شود**. این تنها راه نشتی است: پستی که
  قضاوت نشده (حتی تبلیغ) هنگام خرابی گیتوی می‌تواند به کانال برود. برای دیدن
  این موارد در لاگ:

  ```shell
  journalctl -u bale-news-digest.service --no-pager | grep -E "خطا در سنجش اهمیت|\[ \? \]"
  ```

  هر شکستِ پاسخ بی‌استفاده — چه در سنجش اهمیت و چه در خلاصه‌ساز —
  **پاسخ خام مدل و `finish_reason`** را هم لاگ می‌کند
  (`finish_reason=length | پاسخ خام: '…'`) تا معلوم شود مدل چه گفته بود؛ دیدن
  `finish_reason=length` یعنی پاسخ به سقف توکن خورده و بریده شده است.
- تلاش دوباره فقط وقتی نجات می‌دهد که بکاند خرابِ گیتوی جواب بدِ تصادفی
  بدهد. روتر به یک اتصال می‌چسبد، پس هر ۴ تلاش یک پست به همان بکاند می‌رود
  (۲۵ سپتامبر ۲۰۲۶: بکاندی پاسخ‌هایش را در ۴۰۹۶ توکن می‌بُرید و ۹ پست در یک
  پنجرهٔ ۳ ساعته بی‌داوری به کانال رفت). برای دیدن اینکه هر درخواست به کدام
  بکاند رفته:

  ```shell
  sqlite3 "file:$HOME/.9router/db/data.sqlite?mode=ro" \
    "select substr(timestamp,12,8), model, promptTokens, completionTokens
     from usageHistory where promptTokens between 550 and 850
     order by timestamp desc limit 20;"
  ```
- `sid` هر پست دقیقاً `"{rid}-{date}"` است، همان چیزی که API بله می‌دهد؛ همین
  باعث می‌شود dedup با `news_posts.json` بدون تغییر کار کند و خبری دوباره ارسال نشود.
- برای پاسخ‌دهی ربات در PV، حتماً سرور باید با HTTPS در دسترس باشد.

## ضمیمه‌ها (عکس/ویدیو/صوت/فایل)

پست‌های دارای ضمیمه همراه خلاصه ارسال می‌شوند. چند نکته:

- عکس و ویدیو در API بله هم به شکل `documentMessage` می‌آیند (نه
  `photoMessage`/`videoMessage`)؛ نوع ضمیمه از روی `mimeType` تعیین می‌شود.
- LoadHistory هیچ `file_id` نمی‌دهد — فقط `url` امضاشدهٔ عمومی. پس متد ارسال
  (`sendPhoto`/`sendVideo`/`sendAudio`/`sendDocument`) همان URL را می‌گیرد و
  **خود بله** از آن دانلود می‌کند؛ نه دانلودی سمت ما انجام می‌شود نه آپلودی.
- کپی/فوروارد سمت‌سرور (`copyMessage`/`forwardMessage`) ممکن نیست: ربات به کانال
  مبدأ دسترسی ندارد و `file_id` هم در دست نیست.
- متن خبر بدون خود ضمیمه به مدل می‌رود، ولی مدل می‌داند ضمیمه‌ای هست
  (برچسب نوعش را می‌گیرد) تا خلاصه مثل خبر عادی نوشته شود و مستقیم به
  عکس/فیلم اشاره نکند.
- متن پیام عادی فرستاده می‌شود و فقط خط آخرش عبارت «لینک خبر مرجع» به شکل
  لینک مارک‌داون (`[لینک خبر مرجع](url)`) است؛ بله خودش آن را رندر می‌کند و
  `parse_mode` لازم نیست.
